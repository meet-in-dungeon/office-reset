# 팀 협업 규칙

4명이 짧은 기간에 개발하므로 규칙은 최소한으로 둔다.

> AI(Claude Code, Codex)가 따르는 공통 규칙은 [AGENTS.md](../AGENTS.md)가 기준이다. 이 문서와 내용이 다르면 `AGENTS.md`를 따른다. 규칙을 바꿀 때는 팀원 합의 후 `AGENTS.md`를 먼저 고친다.
> 팀원별 AI 프롬프트는 [AI_PROMPTS.md](AI_PROMPTS.md)에 있다.

## 1. 기본 규칙

- 모든 팀원은 새 프로젝트를 만들지 않고 이 저장소 하나에서 개발한다.
- `main`에 직접 push 하지 않는다. 항상 PR로 합친다. (GitHub 설정으로 승인 1명이 없으면 병합이 막혀 있다)
- PR은 팀원 1명 이상의 승인을 받은 뒤 병합한다. 내 PR은 내가 승인하지 않는다.
- 브랜치는 `feature/`, `fix/`, `chore/`, `docs/` 중 하나로 시작한다.
- `main`은 언제나 `npm run build`가 성공하는 상태로 둔다.
- 병합이 끝난 브랜치는 GitHub가 자동으로 지운다. (설정 켜짐 확인)

## 2. PR은 "작업이 끝났을 때" 한 번만 올린다

PR은 "검토하고, 합칠지 결정해 달라"는 **요청**이다. PR이 하나 생길 때마다 누군가의 작업이 멈추므로, 중간 저장에는 PR을 쓰지 않는다.

| 하는 일 | PR이 필요한가 |
|---|---|
| 작업 중 저장 (`git commit`, `git push`) | **필요 없다.** 내 브랜치에 얼마든지 올려도 된다. |
| 작업 단위 하나가 완료 기준을 채우고 내 컴퓨터에서 테스트까지 끝났다 | **PR 1건** |
| 코드와 함께 바뀐 문서 | **같은 PR에 넣는다.** 문서만 따로 올리지 않는다. |
| 문서만 바꾸는 일 | 하루에 한 번, 모아서 PR 1건 |

- 한 사람이 하루에 올리는 PR은 **1~2건**을 기준으로 한다. 작업 단위는 [WORK_UNITS.md](../WORK_UNITS.md) 4번 표의 한 줄이다.
- 작업 단위가 아직 끝나지 않았다면 "일단 PR부터"가 아니라 push만 한다. (Draft PR도 만들지 않는다)
- PR을 올린 뒤 바로 단톡방에서 "봐 주세요"라고 부르지 않는다. 아래 리뷰 시간에 본다. 막혀서 급할 때만 부른다.

### PR을 기다리는 동안

기다리며 멈추지 않는다. 앞 PR 브랜치에서 다음 브랜치를 따서 계속 개발한다.

```bash
git switch feature/내-앞-작업        # 이미 PR을 올린 브랜치
git switch -c feature/내-다음-작업   # 여기서 다음 작업 시작
```

앞 PR이 병합되면 `main`을 가져와 합친다. (CONTRIBUTING 5번) PR을 올린 브랜치에는 더 이상 커밋을 추가하지 않는다. 리뷰어가 본 내용이 바뀌기 때문이다. 리뷰어가 고쳐 달라고 한 경우만 예외다.

## 3. 리뷰 규칙

- **리뷰 당번을 하루 한 명 정한다.** 그날 올라온 PR을 당번 한 명이 모아서 승인한다. 나머지 세 명은 리뷰 때문에 끊기지 않고 개발에 집중한다. 당번표는 [WORK_UNITS.md](../WORK_UNITS.md) 4-1번에 있다.
- **당번 본인의 PR은 그날 당번이 보지 않는다.** 당번표에 적힌 "당번의 PR을 보는 사람"이 본다.
- **리뷰 시간은 "PR 승인 시간"이다.** 하루 2번(14:30, 17:00)이다. 점심시간을 피했고, 오후 첫 번째는 14:00 중간 점검에서 시연을 본 직후에 바로 승인하고, 두 번째는 17:30 점검 전에 끝내서 점검 때 병합 결과를 공유한다. (시각은 팀이 바꿀 수 있다) 중간 점검은 진행 상황을 나누는 시간이고, 코드를 승인하는 시간이 아니다.
- **다른 사람이 PR 때문에 막혀 있으면 리뷰 시간을 기다리지 않는다.** 당번이 바로 본다.
- 리뷰에서는 아래 4가지만 본다.
  1. `npm run build`가 성공한다.
  2. 담당 파일 밖이나 공통 파일이 바뀌지 않았다. (바뀌었다면 PR 설명에 이유가 있다)
  3. 새 라이브러리나 비밀 키가 없다.
  4. 해당 화면이 브라우저에서 열린다.
- 큰 문제(빌드 실패, 비밀 키, 동작 안 함)가 아니면 취향 차이로 막지 않는다. 고칠 점은 댓글로 남기고 승인한다.
- 해커톤이므로 "완벽"보다 "동작하고 합칠 수 있는 상태"를 우선한다.

## 4. 담당 업무 나누기

- 기능 단위로 나눈다. 한 사람이 한 기능의 화면과 로직을 함께 맡는다.
- 누가 어떤 파일을 맡는지는 [WORK_UNITS.md](../WORK_UNITS.md) 4번 표에 있다. 이 표가 기준이다.
- 작업을 시작하기 전에 "이 기능 시작합니다"를 단톡방에 한 줄 남긴다.
- 내 담당이 아닌 파일은 고치기 전에 담당자에게 먼저 말한다.

## 5. 같은 파일을 두 명이 고치지 않는다

- **파일 하나에는 담당자 한 명만 둔다.** 한 기능을 둘이 나눠 맡으면 파일을 따로 만든다.
  - 예: 스트레칭 화면 `Stretch.jsx`는 원규, 영상 재생 `StretchVideo.jsx`와 음성 `voice.js`는 진수. 화면 파일은 영상 파일을 불러다 쓰기만 한다.
- 파일을 합치는 쪽(불러다 쓰는 파일)의 담당자를 정해 둔다. 두 사람이 만나는 지점은 **한 줄**로 끝나게 만든다.
- 기능마다 새 파일로 만든다. 예: `src/pages/Timer.jsx`, `src/components/StretchVideo.jsx`
- 하루에 한 번 이상 `main`을 내 브랜치에 합쳐 둔다. ([CONTRIBUTING.md](../CONTRIBUTING.md) 5번)

## 6. 상대 기능이 아직 없을 때는 목업으로 테스트한다

"백엔드 붙여서 테스트하자 → 상대는 준비 안 됨" 상황을 만들지 않는다. 합쳐서 테스트하기를 기다리지 않는다.

- 데이터를 주고받는 형식은 [ARCHITECTURE.md](ARCHITECTURE.md) 5, 6번에 정해져 있다. 이 형식 그대로 **가짜 데이터(목업)**를 만들어 내 화면을 테스트한다.
- 이 서비스는 서버 없이 `localStorage`에 저장하므로, 목업은 "저장소 키에 샘플 데이터를 넣는 것"으로 충분하다. 앱 코드를 바꾸지 않는다. (예: `routineLogs` 키에 샘플 기록 3건)
- 목업 파일은 `src/mocks/`에 있다. 이미 만들어 둔 샘플(`routineLogs`, `badges`, `timer`)과 넣는 방법은 [src/mocks/README.md](../src/mocks/README.md)에 있다. 화면 코드에서 불러다 쓰지 않는다. 실제 기능이 합쳐진 뒤에는 목업이 없어도 동작해야 한다.
- 없는 샘플이 필요하면 AI에게 이렇게 요청한다: "상대 기능이 없으니 src/mocks/README.md 방식대로, ARCHITECTURE.md의 데이터 형식에 맞는 목업을 만들어서 내 화면을 테스트해 줘."
- 데이터 형식을 바꾸고 싶으면 받는 사람과 먼저 합의하고 ARCHITECTURE.md를 고친다.

## 7. 공통 파일과 의존성 변경 규칙

공통 파일은 아래와 같다.

- `package.json`, `package-lock.json`
- `vite.config.js`, `index.html`
- `src/App.jsx`, `src/main.jsx`, `src/index.css`, `src/App.css`
- `src/lib/config.js`, `src/lib/router.js`, `src/lib/storage.js`

규칙:

- **의존성과 설정**(`package.json`, `package-lock.json`, `vite.config.js`, `index.html`)은 기능 PR에 섞지 않고 `chore/` 브랜치로 따로 PR을 만든다.
- 그 밖의 공통 파일은 내 기능에 꼭 필요한 **최소한의 줄**만 기능 PR에 포함해도 된다. 이때 PR 설명의 "공통 파일 변경" 칸에 어느 파일을 왜 바꿨는지 적는다. PR을 최소화하려는 규칙이다. (팀장 승인 2026-11-24)
- 새 라이브러리(`npm install 이름`)를 추가하기 전에 단톡방에 알린다. 정말 필요한지, 비슷한 것이 이미 있는지 확인한다.
- `package.json`을 바꿨다면 `package-lock.json`도 함께 커밋한다. 다른 팀원은 병합 후 `npm install`을 다시 실행한다.
- `package-lock.json`에서 충돌이 나면 직접 고치지 말고 팀장에게 말한다.
- 비밀 키, 비밀번호, 토큰은 코드나 문서에 적지 않는다. `.env`에만 적고 팀원에게는 따로 안전하게 전달한다.

## 8. AI(Claude 등)로 코드를 작성했을 때

AI가 쓴 코드도 내 코드다. PR을 올리기 전에 아래를 확인한다.

- [ ] 코드가 무슨 일을 하는지 읽고 설명할 수 있다.
- [ ] `npm run build`와 `npm run lint`가 통과한다.
- [ ] 브라우저에서 직접 눌러 보고 동작을 확인했다. (모바일 화면 크기 포함)
- [ ] 요청하지 않은 파일이 바뀌지 않았다. (`git status`, `git diff`로 확인)
- [ ] 새 라이브러리가 몰래 추가되지 않았다. (`package.json` 확인)
- [ ] 비밀 키나 개인정보가 코드에 들어가지 않았다.
- [ ] 남의 담당 파일이나 공통 파일을 마음대로 고치지 않았다.

AI에게 작업을 시킬 때는 "내 담당 파일 안에서만 작업해 줘"라고 범위를 알려 준다. 복사해서 쓸 프롬프트는 [AI_PROMPTS.md](AI_PROMPTS.md)에 있다. AI가 만든 PR임을 숨길 필요는 없다. PR 템플릿의 AI 사용 칸에 적는다.

## 9. 노션 기록과 문제 공유

- 주요 진행 상황, 다른 팀원에게 영향을 주는 변경, 오류와 해결 과정은 노션 **실시간 전달 사항**에 기록한다. 채팅으로 말한 내용도 빠지지 않게 남긴다.
- 20~30분 이상 해결되지 않는 문제는 혼자 붙들지 않고 팀원에게 공유하고 도움을 요청한다.
- 개별 기능의 완성보다 전체 서비스의 완성을 우선한다. 내 기능이 막혀도 다른 기능이 돌아가게 둔다.
- 공통 협업 규칙(`AGENTS.md`, 이 문서)은 팀원 합의 후에만 바꾸고, 바꾼 뒤 팀원에게 알린다.
